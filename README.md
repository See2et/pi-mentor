# Pi Mentor

普段の Pi チャットで、自分の仮説を考え、批判に弁護し、必要な実装・検証につなげる拡張です。AI は相談位置や検討対象を整理したときに短く知らせます。相談モードの切替、採用、実装開始、修正開始、受け入れには本人の明示的な承認が必要です。普通の返事や相づちは承認にならず、採点や理解度スコアもありません。

## 読み込む

Pi 1.0.4 / Node 24 で確認しています。このリポジトリで実行してください。

```sh
pi --extension .
```

現在の Pi モデルと認証をそのまま使います。別プロバイダへの呼び出しや認証の変更は行いません。

## 使う

1. `/mentor` で開始し、作りたいものや困っていること、目標・制約を普通のチャットで相談します。
2. **仮説形成**では自分で仮説を作ります。AI は考え方や前提を質問・確認しますが、方法や解決策を勧めません。**批判・弁護**では AI が積極的に批判し、代替案や改善案も示します。自分の仮説を弁護し、比較しながら考えます。
3. AI はモードの切替を提案できますが、自動では切り替えません。`/mentor` の操作選択かネイティブ承認カードの明示的な承認で切り替えます。どちらのモードにも戻れます。一つの相談で仮説 A・B と関連論点 C を扱え、対象を追加・参照してもモードは変わりません。各仮説は論点内の版として区別され、以前の仮説・批判・応答・判断は履歴に残ります。古い版の参照だけで以前の採用を現行に戻すことはありません。

本人の判断が必要なところでは、AI が正確な内容と効果を示す一回限りの承認カードを開きます。初期選択は取消です。入力欄の上には現在の相談と次に選べる進み方を一行で表示し、一時停止・保存エラーを優先します。全体整合性・まとめ・終了を順に通る必要はありません。

`/mentor` のカードから自分で次の一手を選ぶ方法も使えます。「議論を続ける」は変更せずに閉じ、操作を選ぶとその場で適用します。後続の確認ダイアログはありません。選択自体では推論を始めません。

カードは操作・対象・効果の要点を表示します。d で正確な全文を開き、PgUp/PgDn・Home/End で読めます。詳細画面の Enter／Esc は未承認のままカードに戻り、取消側の選択に戻します。カードでは ↑↓ で操作を選び、Enter で実行、Esc で取消です。`/mentor` のカードは「議論を続ける」、承認カードは「取り消す」が初期選択です。未解決事項があっても、本人が留保して進めます。AI の合格判定は不要です。

「この条件も含む案を考えたい」と話せば、AI は利用者の仮説を未確認の新しい検討対象として整理できます。対象の整理はモードの切替や採用ではありません。段階を省略したいときや、「この範囲で始める承認画面を出して」のような操作依頼には、正確な内容を示す承認カードを使います。表示内容への明示的な承認で、その操作一回だけを適用し、後続の操作は自動実行しません。依頼文や普通の同意、AI の提案・引用は承認になりません。取消・拒否の後は、新しい明示的な依頼なしに再提示しません。高度な管理操作や任意の操作列は対象外で、ネイティブ承認は対話型 TUI のみ対応します。

「その他…」には今回だけのヒント、理由・留保の編集、相談モードの切替、設計への戻り、履歴、以前の相談への切替、一時停止があります。ヒントと「相談の続きを問いかけてもらう」は通常の Pi 推論を依頼します。ヒントは**今回の応答だけ**に適用され、仮説形成では方法の推薦ではなく問いかけに限定します。

- `/mentor status`：全記録をチャットに表示。
- `/mentor pause`：通常チャットへ戻る。一時停止中は Mentor の指示を注入せず、AI の記録操作も拒否します。
- `/mentor resume`：再開。

Mentor は起動・復元時と記録更新時に Pi 組み込みの codemode を有効にします（一時停止中の status 閲覧にも使用）。他のツール選択は維持します。AI の `mentor_status`・`mentor_record`・`mentor_next` は codemode から呼び出します（`describeTool` で schema を確認）。status は既定で現在の要約を返し、`{view:"issue",issueId:N}` / `{view:"unit",unitId:N}` で対象の全履歴、`{view:"full"}` で枝の全記録を取得できます。省略内容と取得方法も返します。本人へのネイティブ承認 `mentor_assist` はスクリプトから呼べません。

Esc で閉じても記録は変わりません。履歴の閲覧画面の Enter は戻るだけです。候補の作成後やカードを開いている間に記録・コード・セッションが変わった場合は、古い内容での確定を拒否します。候補を整理し直してください。

以前の手動操作は `/mentor advanced` と既存のショートカットに残していますが、通常の導線では使いません。

## 実装・検証に進む

設計の相談から、目的・参照・範囲・期待・非目標・検証計画を示した「この範囲で実装・検証を始める」を一度承認すれば、その正確な範囲だけの実装・検証を許可します。先に方向の暫定採用や範囲だけの確認を済ませる必要はありません。これらは任意の操作として残しており、選んでも実装は始まりません。仮説を確かめる実験も、設計採用とは別の範囲として選べます。

通常の Pi ツールで実装・検証し、AI が実観測ソースに紐づく証拠を記録します。「この結果を確かめる」で実装を止め、期待ごとの観測、参照・コマンド・結果、実対象／代替／未検証、限界を相談します。その後、留保込みの受け入れ、同じ範囲の修正開始、設計への戻り、保留を本人が選びます。受け入れ後は、結果を目標に照らしたり、次の論点を相談したりできます。相談に戻っても次の作業や過去の作業は始まらず、新たな開始には正確な範囲の承認が必要です。

テスト成功や理解度の試験は合格条件ではありません。証拠不足のままでも本人が判断できます。実験の受け入れは、設計や機能の採用を意味しません。

ソースの識別対象は、**Git 追跡ファイル（変更・削除を含む）と ignored でない未追跡ファイルの内容**です。自動コミットはしません。契約や内容が変わると、過去の証拠・受け入れは履歴に残り、現行扱いではなくなります。

ソースは status・メニュー・判断直前・Pi ツール境界で再観測します。Git 外、サブモジュール／特殊ファイル、ツール実行中など観測できない場合は鮮度不明です。最終確認時の一致を示すもので、原子的なスナップショットやライブ監視ではありません。ignored ファイル、リンク先の外部内容、外部サービス、依存環境の状態は保証対象外です。

## 保存と制限

**新規セッションでメニューだけを操作して終了すると、記録は残りません。** Pi は実際のユーザーまたはアシスタントのチャットメッセージがあるまで、新規セッションをディスクへ保存しません。最初の通常チャット後は、それ以前の Mentor 記録も保存されます。`--no-session` では常にメモリ内のみです。

記録は Pi のセッションエントリに保存し、現在の枝だけから復元します。再開・分岐・ツリー移動・再読み込みに追従し、旧 schema 1 の設計記録も履歴を保って読み込みます。相談モード・対象の追加情報がない旧 schema 2 は既存の相談位置から表示を導き、過去の記録や候補の鮮度を変更せず復元します。破損・未対応データでは変更を止め、`/mentor` で確認付きのリセットを選べます。過去のエントリは削除しません。

AI の記録操作と相談整理は別です。相談整理は目標・論点・仮説・参照対象を記録できますが、教育上のモードは切り替えません。本人判断、範囲の確定、実装の開始・再開、作業単位の切替、受け入れもできません。仮説形成で推薦しないことや、批判・弁護で深く検討することはモデルへの指示であり、発話内容を機械的に判定するものではありません。通常の Pi ファイル操作ツールはそのまま使えるため、**書き込み禁止のサンドボックスではありません**。記録はセッションに平文で残るため、秘密情報は入力しないでください。

## 開発時の検証

ワークフローの改善を考えるときは、[`src/domain/design.ts`](src/domain/design.ts)（設計の検討・版ごとの記録）、[`work-unit.ts`](src/domain/work-unit.ts)（契約・証拠・本人判断）、[`workflow.ts`](src/domain/workflow.ts)（遷移と権限）、[`approval.ts`](src/domain/approval.ts)（候補・承認の鮮度）と、対応する [`tests/domain/`](tests/domain/) から確認できます。表示・プロンプトは `src/presentation/`、保存の復元は `src/persistence.ts`、Pi との接続は `src/extension.ts` に分けています。

依存管理には pnpm 11.25.0、開発ツールの実行には Bun 1.3.13 以降を使います。Pi の実行には引き続き Node 24 が必要です。

```sh
pnpm install --frozen-lockfile
pnpm check
```

`check` は型検査、依存方向の検査、直接 `throw` の検査、Vitest を実行します。個別には `pnpm typecheck` / `pnpm architecture` / `pnpm lint` / `pnpm test` を使えます。

`pnpm install` で Git フックも設定されます。コミット前に staged のコードだけを Oxfmt → Oxlint の順で処理し、失敗時はコミットを止めます。JSON・Markdown・YAML は Oxfmt のみ実行します。整形結果はコミット対象に反映され、部分ステージングしたファイルの未ステージ変更は保持されます。全体を手動で整形・確認する場合は `pnpm format` / `pnpm format:check` を使えます。
